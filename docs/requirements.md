# 周赛业务需求

## 周期与状态

- 周赛周期为北京时间每周一 12:00 至下周一 12:00，时间范围左闭右开。
- 状态流转为 `preparing → active → settling → finished`。
- `preparing` 可以累计新周期积分，但分组完成前不展示排行榜。
- 12:00 后的积分必须进入新周期，不等待旧周期结算完成。

## 用户、段位和学段

- 用户当前段位为 1～5，新用户默认段位 1。
- 用户资料保存当前学段；分组时把学段复制到 `period_members.stage`。
- 周期内学段快照不变，即使用户资料中的学段发生变化。
- 当前分组只按段位进行，冻结学段不作为分组条件。

## 积分

- 三个渠道分别配置每日积分上限，所有渠道合计每日最多 500 分。
- 一次行为达到渠道配置的最小时长后才能得分，默认 180 秒。
- 上游必须提供全局唯一来源事件 ID，重复事件不得重复加分。
- 加分同时更新事件流水、每日渠道汇总和周期积分汇总。

## 排名

- 用户只能查看本组最多 50 人的排行榜。
- 排名依次按：积分降序、达到当前积分时间升序、用户 ID 升序。
- 每次积分发生变化，都用服务端处理时间更新 `reached_at`。
- 零积分用户的 `reached_at` 为空，统一排在同分的有效到达时间之后，再按用户 ID 排序。

## 结算与升降级

- 每组独立结算，晋升人数为 `ceil(实际人数 × 晋升比例)`。
- 段位 1～5 的晋升比例依次为 80%、70%、60%、50%、40%。
- 晋升用户升一级，其他用户降一级；段位限制在 1～5。
- 结算结果冻结最终积分、名次、到达时间、学段、原段位和新段位。
- 12:00 只生成任务，结算默认延迟 5 分钟启动。
- 每 100 个小组一个批次，最多约 5000 人；结算与段位更新分别提交。
- 默认全局只允许一个 Worker 重任务执行，避免多实例叠加数据库压力。
- Worker 批次之间默认至少间隔 1 秒，避免持续无间隔写入数据库。

## 分组

- 结算完成并更新用户段位后，为新周期重新分组。
- 同一段位使用 `hash(period_id,user_id)` 稳定打散，每组最多 50 人。
- 同一个周期重复执行分组必须得到相同结果。

## 奖励

- 每个段位配置独立奖励。
- 用户达到某个段位后，自动补齐该段位及以下尚未发放的奖励。
- 同一用户、同一段位终身只能发放一次。
- 奖励任务分批执行，并使用稳定幂等键支持安全重试。
- 奖励每批最多处理 1000 条，默认与结算任务串行执行。
